# Pickup Radar v2.3

面向中国大陆 Apple Store 到店取货场景的高可靠库存查询与到货监控 Web App。零运行时依赖，仅需 Node.js 20+。

核心原则始终只有三条：

1. **只把 Apple 明确返回的 `available` 当作有货。**
2. **查询失败、结构变化、门店缺失与"无货"严格分离。**
3. **服务端合并查询，绝不让每个用户各自去压 Apple。**

## v2.0 做了什么

v1.1 有一个从原理上就不成立的假设：用一个 seed store 查询，期待 Apple 返回整座城市的门店。实测下来 `store=R320` **只返回 1 家门店**，于是北京 6 家店里有 5 家永远是 `unknown`。

v2.0 围绕这一点重建了数据层，并把整套系统提升到可长期运行的水准。

### 0. 多机型（v2.1）

目录、监控、告警与前端全部按**机型**维度组织。两款机型的发售时间线互相独立：

| 机型 | SKU 数 | 预购 | 发售 |
|---|---|---|---|
| iPhone 18 Pro Max | 16（4 容量 × 4 色） | 2026-09-12 20:00 | 2026-09-18 |
| **iPhone Duo**（折叠） | **8**（4 容量 × 2 色） | **2026-10-16 20:00** | **2026-10-23** |

关键点：

- **阶段按机型独立判定**。全局 `launchPhase()` 会让一款机型被另一款的时间线误伤。
- **未开售机型不消耗上游预算**：监控轮直接跳过，`/api/availability` 返回 `gate` 而不触达 Apple。
- **可提前布控**：Duo 还没预售，但现在就能建好关注，10 月 16 日窗口一开自动开始查询。
- **SKU 是从 Apple 自有产品数据读取的真实零件号**，不是推测。测试强制校验 CH/A 格式与跨机型唯一性——错误的 SKU 会永远返回 `unknown`。

### 1. 数据正确性

| 项 | v1.1 | v2.0 |
|---|---|---|
| 单次请求解析的北京门店 | 1 / 6 | **6 / 6** |
| 请求参数 | `store=<seed>` | `store=<anchor>&searchNearby=true` |
| 跨城复用 | 无 | 一次请求可同时填充邻近城市 |

`searchNearby=true` 让端点返回一个**门店簇**，而不是单店。北京锚点会连天津一起返回，上海锚点会连苏州、无锡、宁波一起返回。

### 2. 覆盖规划器（集合覆盖）

既然一次请求能跨城，监控一轮就不该是"每城一请求"。`src/coverage.mjs` 把它建模成**加权集合覆盖**，用贪心算法选出能覆盖全部被关注城市的最小锚点集合。

安全规则：只有当某城的**全部**门店都在某锚点的响应中出现过，才判定该锚点覆盖该城。判断错了最多退化成 `unknown`，永远不会产生假的"无货"。

实测：北京 + 天津 → **1 次请求**；上海 + 苏州 + 无锡 + 宁波 → **1 次请求**。

Apple 单次请求可接受全部 16 个 SKU，因此"整条产品线 × 一个门店簇"就是一次请求。

### 3. 弹性（对标 resilience4j / Envoy）

- **三态熔断器** closed → open → half-open。half-open 只放行**限量探针**，恢复中的上游不会被排队请求一次性冲垮；连续熔断按指数退避。
- **全抖动指数退避重试**，只对幂等 GET 且真正瞬时的故障（超时、socket 错误、非限流的 5xx）重试。
  - **限流（429 与 Apple 非标准的 541）不在请求内重试**。实测几秒内重试几乎总是再次被限流，约 250 次重试只救回十几个请求，反而加深限流；限流直接计入熔断器，由监控放慢节奏。
- **令牌桶 + 并发信号量**：对 Apple 的持续速率和突发额度都有上限，无论有多少关注。
- **请求合并**：相同锚点的并发请求只发一次。

### 4. 自适应轮询

固定 30 秒是两头不讨好：发售日太慢，发售三周后的凌晨四点纯属浪费。v2.0 的节奏由**发售阶段 + 观测到的波动 + 上游健康度**共同决定：

| 情形 | 节奏 |
|---|---|
| 预售/发售窗口前后 | 最快（10s） |
| 刚发生过状态变化 | 基准节奏 |
| 长期无变化 | 逐级拉长，最长 60 秒（`MONITOR_QUIET_MAX_MS`）；重启后从启动时刻起算 |
| 熔断打开 | 遵守熔断冷却，不再压上游 |
| 被 Apple 限流 | 以上节奏乘以限流系数：每次限流翻倍（最多 32 倍，且不超过 15 分钟），之后每成功一轮缩短 20%。网页查询触发的限流同样计入 |
| 无人关注 | 最长间隔 |

新增关注会立刻**唤醒**调度器，不必空等一个长睡眠。

网页的后台自动刷新带 `auto=1`，两分钟内（`PAGE_REFRESH_MAX_AGE_MS`）的缓存直接复用，不再每 15 秒请求一次 Apple；手动刷新仍然实时查询。

轮询之外，**任何一次新鲜的 Apple 读数**（页面刷新、跨城收割顺带拿到的城市）落入缓存时都会立即对照关注判定，不额外消耗上游请求；轮询轮次只是兜底。

### 5. 告警质量

- 首次成功查询只建立基线，**永不**误报。
- 只有**进入** `available` 才告警；`unknown → available` 算真实到货。
- 每个 (关注, 门店) 有**冷却窗口**，门店在边界反复抖动不会刷屏。
- **stale 缓存读数绝不产生到货事件**——过期数据描述的是过去。

### 6. 通知可靠性

外部推送走**带重试的发件箱**（指数退避，耗尽后进死信），不再是即发即忘。
SSE 事件带单调序号，浏览器重连时用 `Last-Event-ID` **重放**断连期间错过的事件——那恰恰是这个应用存在的意义所在的时刻。

### 7. 失败必须可见（v2.3）

上一版有三类故障会**静默发生**，用户和运维都看不出来。这一版全部修掉，每条都有回归测试：

| 故障 | 旧行为 | 新行为 |
|---|---|---|
| Apple 改了响应结构 | HTTP 200 即记为成功，健康页常绿，熔断器永不打开，查询全部退化为 `unknown` | `validateContract()` 在标记成功**之前**校验；硬失败触发熔断并写入 `lastError`、`contractFailures` |
| 单个 SKU 投影失败 | `catch { continue; }` 连日志都没有 | 计入 `parseErrors`、写 `lastParseError`、输出 warn 日志 |
| 落盘失败后关闭 | `close()` 正常返回，进程 `exit(0)`，守护进程以为是正常停止 | `close()` 抛 `STATE_FLUSH_FAILED`，进程 `exit(1)` |
| 未捕获异常 | 走通用 shutdown，`exit(0)` | `exit(1)` |

区分是刻意的：**部分** SKU 缺失只记警告不熔断（可能是真的没上架），**全部**缺失才判为契约破裂。

### 8. 通知投递（v2.3）

投递单位从"事件"改为 **"事件 × 渠道"**：

- 每个 (事件, 渠道) 有独立的重试计数和幂等键，已成功的渠道**不会**因其它渠道失败而重发
- 发件箱持久化到状态文件，重启后续投而非静默丢弃
- 退避期间的任务保存在 `inflight` 中并一并落盘——否则崩溃窗口会吞掉通知

### 9. 前端请求竞争（v2.3）

旧实现 `if (state.loading) return;` 同时犯了两个错：新请求被**直接丢弃**，而旧响应随后渲染在新选择下。

逻辑已抽到 [public/request-guard.js](public/request-guard.js)，前端与测试共用同一份代码，因此这个修复是**可执行验证**的而非仅靠阅读：

- 每个请求带单调序号 + 选择快照，两者都匹配才允许落地
- 发起新请求时 `abort()` 在途请求，而不是跳过新请求
- 被取消的请求不渲染为"查询失败"
- 只有最新请求拥有共享 UI（spinner、自动刷新定时器）

7 项测试覆盖，含一个端到端场景：慢请求（北京）进行中用户切到上海，快请求先返回——断言最终只渲染上海。

### 10. 提前布控（v2.3）

未开售机型可以提前建立关注。语义已明确定义：**提前布控的关注，首次查到有货即视为真实到货并提醒**——用户是在完全买不到的时候布的控，那一刻就是他要等的时刻。普通关注仍然遵循"首轮只建基线"。

`armedBeforeLaunch` 是一次性标记，首轮消费后清除。

### 11. 平台健壮性

- **优雅关闭**：SIGTERM → 停监控 → 落盘 → 退出码 0。
- **持久化**：去抖合并写入 + `fsync` + 原子 rename；损坏文件被隔离而非静默丢弃；带 schema 版本与前向迁移。
  - 修复了 v1.1 的真实缺陷：一次写入失败会让 `writeChain` 永久 reject，之后**所有**写入都失败。
- **限流桶定期回收**（v1.1 中该 Map 永不清理，是内存泄漏）。
- 静态资源支持 **ETag / 304**；缺失资源正确返回 404，而不是用 200 回一个 HTML。
- 结构化日志 + **`/api/metrics`**（Prometheus 文本格式）。

## 本地运行

要求 Node.js 20+，推荐 22/24。

```bash
npm run check   # 语法检查 + 96 项测试
npm run dev
```

打开 <http://localhost:4173>，交互预览 <http://localhost:4173/?demo=1>。

## API

| 端点 | 说明 |
|---|---|
| `GET /api/catalog` | 产品目录与门店清单 |
| `GET /api/availability?product=&capacity=&color=&region=` | 实时库存；机型未开售时返回 `gate` |
| `GET /api/watches` · `POST` · `DELETE /api/watches/:id` | 关注管理 |
| `GET /api/stream` | SSE 事件流（支持 `Last-Event-ID` 重放） |
| `GET /api/events?limit=` | 最近到货事件 |
| `GET /api/health` | 健康检查：`status` 为 `ok` / `degraded` / `down`，并列出 `problems` 与 `warnings`；只有无法发现到货（`down`）时返回 503 |
| `GET /api/metrics` | Prometheus 指标 |
| `GET /api/stats` · `GET /api/stats/events` | 到货统计（见"到货统计"一节） |
| `GET /api/demo?region=` | 交互演示数据，不触达 Apple |

## 状态语义

| 状态 | 含义 |
|---|---|
| `available` | Apple 明确表示可取货 |
| `unavailable` | Apple 明确表示不可取货 |
| `ineligible` | 当前配置/门店不可进行该取货方式 |
| `unknown` | 请求失败、接口结构异常、SKU 缺失或门店响应缺失 |

**`unknown` 永远不能转换为"无货"。** 这条规则贯穿全部代码路径，并有对应测试守护。

## 配置

### 手机推送

关掉网页后要收到到货提醒，至少配置一个服务端推送渠道。可以同时配置多个，各渠道独立重试，互不影响。

| 渠道 | 配置项 | 收在哪里 |
|---|---|---|
| Bark | `BARK_URL`，铃声与响铃方式见 `BARK_SOUND` / `BARK_CALL` / `BARK_LEVEL` / `BARK_VOLUME` | iPhone Bark App |
| ntfy | `NTFY_URL` | ntfy App（服务器在境外） |
| 飞书群机器人 | `FEISHU_WEBHOOK_URL`，开启签名校验时加 `FEISHU_SECRET` | 飞书群 |
| 企业微信群机器人 | `WECOM_WEBHOOK_URL` | 企业微信群 |
| PushPlus | `PUSHPLUS_TOKEN` | 个人微信（PushPlus 公众号） |

配好后运行 `npm run notify:test`，会向所有已配置的渠道发一条测试提醒并打印结果。

飞书、企业微信、PushPlus 被拒收时也会返回 HTTP 200，服务端会检查响应体，拒收计为失败并重试。原因见 `/api/health` 的 `notifications.channels[].lastError`。所有渠道都是全局配置，所有用户的到货都推到同一处。

## 到货统计

入口：首页右上角的统计图标，或直接打开 `/stats.html`。点配置或柱子可下钻，筛选条件同步到 URL。

**口径**（Apple 不返回台数，所以"增加了多少"用状态变化来衡量）：

| 指标 | 定义 |
|---|---|
| 上架 | 某配置在某门店从无货变为有货 |
| 售罄 | 从有货变回无货，并得出这次有货持续了多久 |
| 初次观测 | 第一次看到就已有货，不算上架（没看到它到货） |
| 同时有货 | 某一时刻有货的「门店 × 配置」数 |
| 刷新次数 | 监控轮次 + 页面查询；另列缓存命中、发往 Apple 的请求、重试与失败 |

**规则**

- 按「SKU × 门店」计，不按关注计：多人关注同一配置不会重复计数
- `unknown`（查询失败、门店缺失）不改变状态，绝不记为售罄
- 只从 `harvest` 喂入：只有新鲜且通过契约校验的数据会被记录，缓存命中和降级数据不会制造状态变化
- 按北京时间分天。跨日仍有货的门店写一条 `carry`，每天的文件自成一体
- 服务停机期间发生的变化无法观测：跨停机的售罄标记为 `uncertain`，其时长不计入平均

**存储**：`DATA_DIR/stats/events-YYYY-MM-DD.jsonl`（追加写）、`counters-YYYY-MM-DD.json`、`state.json`，默认保留 30 天（`STATS_RETENTION_DAYS`）。

**接口**

| 端点 | 说明 |
|---|---|
| `GET /api/stats?day=&product=` | 总览：刷新计数、到货/售罄、现在有货门店、每小时到货（含按配置）、配置排行 |
| `GET /api/stats/events?day=&product=&type=&region=&sku=&hour=&limit=&before=` | 记录，最新在前，可按配置与小时筛选，含每小时全量计数 |

## 目录证据链

目录是手工维护的快照。抄错一个 SKU，该配置会**永远**返回 `unknown` 且无人察觉——所以它需要可复核，而不是靠信任。

```bash
npm run verify:catalog          # 从 Apple 重新推导目录并比对，有差异则非零退出
npm run verify:catalog:write    # 同上，并另存带 sha256 的快照到 evidence/
```

校验内容：SKU 存在性（双向）、容量、价格、预购与发售日期、颜色映射的双射关系。
故障注入验证过：把任一 SKU 改错会同时报 `sku-missing-upstream` 与 `sku-new-upstream` 并以非零码退出。

当前状态：**24 / 24 个 SKU 与 Apple 实时数据一致**（16 个 18 Pro Max + 8 个 Duo），价格与容量零差异。

两个实现中踩到的真实陷阱：

- Apple 产品名混用 **U+00A0 不换行空格**（`iPhone\u00a018 Pro\u00a0Max`），直接字符串比较会静默匹配为零——脚本第一版就栽在这里，16 个 SKU 一个都没匹配上。
- 颜色不做字面比较。我们的 `glacier-blue` 是内部 id，Apple 叫 `Glacier`。改为校验**双射**（同一内部色必须映射到同一上游饰面，两色不得撞同一饰面），既能抓出真的串色，又不因命名差异误报。

## 生产部署

**不要把 `setTimeout` 调度的 monitor 直接部署成 Serverless Function**，Serverless 实例不保证常驻。设 `DISABLE_MONITOR=1` 可让 Web/API 层无监控运行。

```text
Web / API  ──┬── PostgreSQL
             ├── Redis
Monitor Worker (常驻)
             │
Apple pickup-message
             │
Notification Worker
```

更完整的演进方案见 `ARCHITECTURE.md`。
